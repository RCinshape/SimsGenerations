# family capture audit

The signed v8 bundle retains the prior collector's compiled `twentygen_sync.pyc`. Its bytecode contains `_family_ids`, `genealogy`, `get_parent_sim_ids_gen`, `get_children_sim_ids_gen`, and `spouse_sim_id`. This is evidence of the source interfaces, not a runtime verification of every branch or completeness. The collector's Python source and a game installation were not available for this audit. The backend stores each sim's own reported parent and child arrays; household membership is a separate observation. The previous UI also derives partner candidates from shared parentage, which is not evidence of romance. A partner's children must never be attributed to the selected sim unless that sim has a direct qualifying parent link.

The current backend cleaner bounds captures to 200 sims, parent lists to 10 and child lists to 30. The existing family merge unions observations rather than removing omitted links. It does not verify save lineage or order: save slots, household IDs and wall-clock timestamps cannot establish lineage across copied saves, rollback or computers. Existing snapshots without the capability object are legacy/unknown. String sim IDs must remain strings end to end; a numeric ID already rounded in JavaScript cannot be recovered.

The addon marks captures `familyCapture.schema = 1`, `completeness = partial`, `saveIdentity = unverified`, and `captureOrder = unverified`. It attempts bounded, read-only direct genealogy generators on each available sim, with per-list `observed`, `partial`, or `unknown` status. A complete direct getter replaces only that person's corresponding list in the stream projection; partial lists add evidence and unknown lists retain it. Missing sims never imply deletion. It persists a local journal stream and capture sequence before sending; those order captures from that journal, not save history. A copied journal or rolled-back save can invalidate even that assumption.

The candidate backend stores each stream separately, keeps at most eight original captures per stream, and rejects duplicate or older sequences from changing that stream. It accepts at most 16 streams per player. An owner must choose the active source with a revision-checked action; the existing unscoped family remains an independent legacy choice. Other streams cannot enter the chosen family or sync projection. After a stream is chosen, its accepted latest capture feeds the normal game sync and goals. No code claims save rollback detection or automatically associates a stream with the legacy family. These controls have synthetic tests; runtime integration and source selection by all players still require verification.

[EA's official February 2026 patch notes](https://www.ea.com/games/the-sims/the-sims-4/news/update-2-3-2026) link to its [genealogy API migration notice](https://forums.ea.com/blog/the-sims-game-info-hub-en/the-sims-4-code-changes-for-modders---feb-3rd-base-game-update/13120743). EA's published code lists `sim_info.genealogy.get_parent_sim_ids_gen()` and `get_children_sim_ids_gen()` as direct ID generators. The addon tries those first and capability-checks the alternative getter names used in the [community library's source](https://github.com/DeviantGameMods/Sims4CommunityLibrary/blob/main/Scripts/sims4communitylib/utils/sims/common_sim_genealogy_utils.py); failures remain unknown. EA also documents read-only family-tree traversal and spouse, fiance and steady flags. The addon samples direct edges for at most four household roots, with at most 128 inspected edges recorded, and retains only explicit flags. Edge absence does not establish divorce or an ended relationship; it makes no parent-direction inference. The game controls traversal internally, so no gameplay performance guarantee has been established. The actual installed game remains unverified. A [modding library's save-slot context](https://github.com/lot51/core-library) identifies a slot but does not establish a stable lineage across save-as, copying, rollback, and multiple computers.

`scripts/build-family-update.py` makes an **unsigned** v9 candidate from the SHA-256-pinned signed v8 bundle, changing only the compiled addon. Python 3.7.17 built the candidate and ran the synthetic collector tests. The v8 signature verifies; the v9 file set, canonical signing manifest, bytecode magic, unchanged other modules and compiled addon against current source were checked. The candidate has no signature and has not passed the trusted updater. It requires the original trusted signer, installation, restart and verification on each supported game setup. No game runtime was available; synthetic tests are not in-game evidence.

## portrait feasibility

No automatic portrait export was proved. The [resource utility documentation](https://sims4communitylibrarywiki.readthedocs.io/en/latest/sims4communitylib.utils.resources.html) demonstrates resource-key creation for images, not retrieval of a current sim portrait's bytes or a mapping from an exact save-scoped sim to its portrait. A [package-tool author's resource inventory](https://github.com/ssinakhot/sims4-workspace/blob/main/RESOURCE_TYPES.md) identifies package image types and extraction tooling; it does not establish a portrait-to-sim mapping. A [manual cache extraction account](https://modthesims.info/t/598287) reports visually selecting and exporting generated thumbnails. That is useful investigative evidence, but it is not a reliable automated identity mapping, a generation API, or proof of cache availability after eviction.

A real-game proof still needs matching individual images for several exact IDs including an off-lot sim and infant or toddler; repeat tests after reload, cache eviction and appearance changes; measured game-thread performance; and bounded retry, content hashing, size limits and stale-version checks. Manual portraits remain pinned. Do not upload guessed cache matches or enable automatic replacement until that proof passes.
